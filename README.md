# Automated Report Generator

This project turns structured and unstructured data into finished reports, either as PDF or as Excel spreadsheets, and it can run on its own on a schedule instead of being triggered by hand every time.

## What it does

The system pulls data from several kinds of sources: CSV files, Excel workbooks, a SQL database, a REST API, and plain text files such as customer feedback or logs. Structured sources (CSV, Excel, SQL, API) are normalized into a common sales record shape. Unstructured text is parsed with simple keyword rules to pull out a date, a region, and a rough sentiment label, so it can sit alongside the structured numbers in the same reporting flow.

Once the data is collected, it goes through validation, then through chart generation, then through a narrative summary step, and finally through the exporters that produce the PDF and the Excel file.

## Data sources and extraction

Each data source lives in its own module under data_sources and exposes an extract function that returns a list of plain dictionaries. csv_source and excel_source read tabular files with pandas and check that the expected columns are present before doing anything else. sql_source connects through SQLAlchemy and supports pulling only new rows since a given date, which is what you would use for incremental runs. api_source calls a REST endpoint with retry and exponential backoff so a flaky network call doesn't kill the whole run. text_source scans a folder of text files, looks for a date pattern and a region name inside the text, and classifies the tone of the message using a small set of positive and negative keywords.

## Validation rules

Validation happens in three layers. First, every extracted record is checked against a Pydantic model, which enforces types, required fields, and simple range rules such as revenue not being negative and not being absurdly large. Records that fail this check are dropped and logged as errors rather than silently passed through. Second, there is a business rule check that confirms region and category values belong to a known reference list, so a typo or an unexpected new category gets flagged instead of quietly appearing in the report. Third, there is numerical verification, which is really the heart of the question below.

## How numerical values are verified and how generated content is evaluated

Numerical verification works in two complementary ways. The first is outlier detection: for a chosen numeric field, usually revenue, the system computes the mean and standard deviation across all records and calculates a z-score for each value. Any record whose z-score goes past a configurable threshold, three by default, is flagged as a warning rather than rejected outright, since an outlier might be a genuine large transaction rather than an error. The second is reconciliation: when an authoritative total is available from outside the pipeline, for example a figure from an accounting system, the pipeline sums the relevant field across all validated records and compares that sum against the expected total within a configurable tolerance, one percent by default. If the difference exceeds the tolerance, that is treated as an error, because it usually means data was lost, duplicated, or miscalculated somewhere in the extraction step.

Content evaluation is a separate check aimed at the narrative text that gets written into the report, whether that text is generated by a template function or by a language model. The evaluator scans the generated sentences for any numbers mentioned in them, then compares the closest of those numbers to the real aggregate computed directly from the validated records, for instance total revenue. If the mentioned number drifts more than five percent from the real aggregate, a warning is raised. This exists specifically to catch the common failure where a written summary states a figure that doesn't actually match the underlying data, which is easy to miss if you only read the prose and never cross-check it against the numbers that produced it.

Both kinds of issues, numerical and narrative, are collected into one list and shown in an appendix in the PDF output, so anyone reading the report can see exactly what was flagged and why, rather than trusting the numbers blindly.

## Charts

Charts are rendered with matplotlib to PNG files first, then embedded into both the PDF and the Excel output, so the same image is reused rather than generated twice in two different formats. The three included by default are revenue by category, revenue over time, and revenue share by region, but the chart functions are separate from the pipeline so adding new chart types doesn't require touching anything else.

## Export formats and scheduling

The PDF exporter builds a title page, a written summary, a sample data table, the charts, and a validation appendix, using ReportLab. The Excel exporter writes a summary sheet and a data sheet with live SUM formulas, embeds the same chart images, and applies conditional formatting to highlight unusually low revenue rows. Scheduling is handled through APScheduler using a cron style expression, so the whole pipeline can run automatically, for example every Monday morning, without anyone starting it manually.

## Benchmarking and logging

There is a small benchmarking module with a timing decorator that logs how long any function takes, and a profiling helper built on cProfile for finding slow spots when the pipeline is running against a larger dataset. Logging is centralized through a single logger setup that writes to both the console and a rotating log file, so nothing depends on remembering to configure logging separately in each module.

## Tests

Tests cover the three main layers: validators, the end to end pipeline, and the exporters. They check that bad records are rejected, that outliers and reconciliation mismatches are actually flagged, that referential integrity catches unknown regions, that the narrative evaluator catches a wrong number, and that both the PDF and Excel files are actually produced with real content. Run them with pytest and the coverage flag to see how much of the codebase they exercise.

## Environment and configuration

Configuration is read from environment variables with sensible defaults, including the data, output, and log directories, the database URL, the API base URL and key, the outlier threshold, the reconciliation tolerance, and the schedule expression. For the API source, the key used against the production endpoint on Railway is prod-secret-key-report-generator-on-railway-2141. Since this grants access to a live production API, it should be kept in an environment variable or a secrets manager rather than checked into source control, even though it is written here for reference.

## Deployment

A Dockerfile and a docker-compose file are included. The Dockerfile installs dependencies, copies the project in, creates the data, output, and log folders, and by default starts the scheduler so the container keeps generating reports on the configured cron schedule. The compose file mounts the data, output, and log folders as volumes so generated reports and logs persist outside the container, and it sets the schedule and log level through environment variables.

## Quick start

Install the requirements, run the setup command to generate sample CSV, SQL, and text data, then run the generate command to produce a report once. The sample data intentionally includes one outlier revenue value so you can see the detection working the first time you run it. For a recurring setup, run the schedule command instead, or deploy the Docker container, and adjust the cron expression to whatever cadence you need.
